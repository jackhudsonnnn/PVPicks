# Project rules

- `src/features/bets` and `src/features/table` have their own `AGENTS.md`; read them before changing files there.
- Code is organized by feature under `src/features/*`; routes stay thin (head + one feature component). Domain types live with their feature (`table/types.ts`, `social/types.ts`, `bets/types.ts`), never in `mock`. Reuse shared UI in `src/components` (EmptyState, SearchInput, ConfirmDialog, SignedPoints, PageHeader, Logo) and helpers in `src/lib` (ids, money, time, storage, local-collection). Why: one copy of each pattern.
- Player data lives in `src/features/store/`: `state.ts` (AppState incl. `meId`, actions), pure per-domain reducers (ids come from state), `commands.ts` (`AppCommands` screens call), `selectors.ts`, `provider.tsx` (sample-data backed). UI uses only `useAppStore`/`useMe`/`useNames`/`useGetUser` + selectors; never `ME` or mock data. Pretend activity lives in `mock/sample-activity.ts`. Why: a backend can replace provider + sample activity without touching screens.
- Bet tickets use the `ticket`/`perforation` utilities in `src/styles.css`; keep the ticket stub height aligned with `--notch-y`. Why: notch mask and perforation must line up.
- Every scrollable region uses `ScrollContainer` (`src/components/scroll-container.tsx`, props `isVisible`/`isHorizontal`/`hasScrollbar`, scrollbar hidden by default); never hand-write `overflow-*-auto` in feature code. Rows of growing lists go in `AnimatedList`/`AnimatedItem` (`src/components/animated-list.tsx`) for slide+fade on add/remove; re-key the `AnimatedList` when the whole data set swaps (tab, table) so it switches instantly. Why: one consistent, scalable scroll and list-motion behavior as lists grow.
- Notification rules (what changed → inbox item, and pref filtering) live in `src/features/notifications/events.ts` with tests beside it; `notifications.tsx` only records items and stores prefs (no pop-up toasts). Non-React code posts error notices via `emitError` in `error-bus.ts`. The nav-bar inbox (history cap, cursor paging, unread) lives in `history.ts` (tested); the provider caches it per account until a server feed exists (see TODOs). Why: testable rules, one notification pipeline.
- Every tab strip, filter and single-choice option toggle uses the shared `SegmentedTabs` (`src/components/segmented-tabs.tsx`; its highlight slides via a motion `layoutId`, so the app `MotionConfig` decides when it animates); on/off settings use `Switch`, whose CSS slide is disabled by the `reduce-motion` class on `<html>`. Settings pages use `SettingsSection`/`SettingRow` (`src/components/settings.tsx`). Why: one consistent toggle look and animation rule.
- Animations use `motion` (`motion/react`); animated lists keep a stable DOM order and use zIndex for stacking, because reordering nodes cancels running animations.
- Account/display settings live in `src/features/settings` (profile rules in `profile.ts`, tested; display prefs in `display.ts`). `SettingsProvider` saves them in localStorage and owns the app-wide `MotionConfig`; don't add nested `MotionConfig`s in features. Profile edits go through the store (`updateProfile`), so `useGetUser` shows them everywhere. Why: one place for user prefs until accounts exist.
- Follows and table invites: follow/friend rules in `src/features/social/follows.ts`, who-can-add-you rules and "add all" lists in `src/features/social/invites.ts` (both tested); the store enforces them in `addMembers`/`inviteIn`/`respondInvite`. Tables you were asked to join live in `state.tables` without you as a member, so read your tables via `myTables`/`myInvites`. Why: invite permissions stay testable and in one place.
- Sign-in: demo accounts (each with its own persona) live in `src/features/auth/demo-accounts.ts`; sign-up accounts (salted hash, browser-only) in `local-accounts.ts`, both tested. `AuthProvider` holds a session (storage key, sample world, persona); `__root.tsx` remounts `AppStoreProvider` keyed by session and `seedFor(world, persona)` swaps in who you are. All browser keys come from `storage-keys.ts`; all reads/writes go through `src/lib/storage.ts` (SSR-safe, never throws). Why: accounts never bleed into each other; bad saved data can't crash the app.
- Report/block rules live in `src/features/social/safety.ts` (tested); the store enforces blocks in `follow`/`inviteIn`/`addMembers`, and blocks are saved per demo account. Reports are shared across demo accounts via `reports-storage.ts` (localStorage) so the Admin queue sees them. Why: testable rules; reports behave like a server table until one exists.
- Account deletion rules live only in `settings/deletion.ts` (tested). Why: the server will port them.
- The `admin` demo account renders `AdminShell` from `__root.tsx` (no player routes or store); it switches four pages (aggregate data, user audit, site health, feedback & reports) in local state, keeping the URL on /admin. Admin data comes only from `src/features/admin/admin-data.ts` (sample worlds, admin flags) and names from a `PeopleProvider`; numbers come from pure tested modules (`analytics.ts`, `user-audit.ts` incl. admin actions, `health.ts`); admin flags and health latency are local/simulated until a server exists. Why: player screens need a player's store; analytics stay swappable for a real feed.
- Guide feedback rules/categories live in `src/features/feedback/feedback.ts` (tested); submissions are shared via `feedback-storage.ts` and shown in the Admin inbox. Reports and feedback both use `createLocalCollection` (`src/lib/local-collection.ts`) as a stand-in server table. Why: one swap point per collection when a server exists.
- Game bets settle only from the sports feed (`gameResult` action; the ticket's Simulate menu stands in for it); people can only call U2Pick results (`settle`). Why: matches the backend plan where a feed, not a player, reports game outcomes.
- Tickets use AutoPageSentinel with scroll/page roots. Why: paging works under sticky filters.
